## PDF 裁边回归（HAM-166）

官方 PDFViewer 替换提交 `233db4f` 将裁边实现为 page div 的 `clip-path`，保留整页布局尺寸；后续集成虽然接通了全局/单页参数和编辑器，页面占位与 `page-width` 仍按未裁切页面计算。实际表现为白边被遮住，但页间空隙和缩放仍然包含白边。生成的 600 × 800 PDF 在 100% 缩放、上裁 10% / 下裁 15% 时，可见页间距从原本 10px 变为约 276px。

修复在保持 PDF.js 原始 page/viewport 与标注坐标的前提下，通过 flex 排版和四边负 margin 扣除裁切占位，并隔离被裁区域的滚动溢出。宽度适配、跳页、阅读位置和编辑模式使用统一的归一化裁切几何；编辑时显示整页，退出后恢复裁切。跳页对齐裁后可见页首。

运行：

```sh
yarn install --frozen-lockfile
node scripts/check-pdf-edge-crop.mjs
```

脚本启动本地 Vite Dev Server，在 Chromium 中通过真实 Reader 打开生成的三页 PDF（包含非零原生 CropBox、旋转页），测量实际页面边界并执行鼠标拖拽。覆盖裁边开关、四边独立生效、全局/单页覆盖、页面浏览器跳页、编辑开关及应用到当前页/全部、文字选择/高亮对齐、50%/200% 缩放、桌面及 480px 视口的裁后宽度适配。修复后可见页间距恢复为约 10px。

PDF 样本、截图及测量报告输出到 `test-results/pdf-edge-crop/`。该目录为运行产物，不提交。

## 切换裁边时保持阅读锚点

扣除裁切占位后，开关裁边会改变前面各页的高度；仅保留原有 scrollTop 会让第 2 页中部的参考内容偏移约 373px。适宽还会改变缩放，因此保存 CSS 页内偏移无法保持同一内容。

`src/pdf/usePdfLayoutAnchor.ts` 在旧布局的 layout effect cleanup 中优先捕获首个可见文字点的 PDF 用户坐标；无文字时捕获第一张可见页与阅读区相交的几何点。经 `convertToPdfPoint` / `convertToViewportPoint` 转换，在新布局应用裁切后恢复。全局/单页裁切、编辑模式、上下及水平留白共用该路径；被裁掉的锚点夹到最近可见边界。过程中暂停发布中间阅读位置，避免进度回显抢占滚动。

PDF.js 异步 canvas 渲染还会通过 `--scale-round-x/y` 再次缩小页面尺寸，影响后续页面位置。因此除连续两帧恢复外，还观察 viewer 的尺寸变化并重新校正；用户滚动、跳页、书签、主动缩放和切换文档会取消恢复。容器禁用浏览器原生 overflow anchoring，避免重复补偿。

浏览器脚本现覆盖 35 项检查。在第 2 页中部，100% 和适宽各反复开关三轮，参考 PDF 点偏移均小于 1px；另覆盖全局上下裁切、当前页及前页单独裁切、进出编辑模式、实际上下留白输入和清空留白，并确认恢复后裁后适宽、跳页对齐仍有效。内容位置断言保持小于 2px；适宽尺寸断言仅允许 PDF.js 实际 `--scale-round-x` 对应的取整损失。`anchor-before.png`、`anchor-enabled.png`、`anchor-disabled.png` 为同一参考位置的截图。

`test/pdf-viewer/pdf-layout-anchor.test.tsx` 补充 PDF 坐标、非零原生 CropBox、90° 旋转、无文字层页面、快速连续裁切、异步前页尺寸变化及导航取消的回归验证。

快速切换还暴露了另一条滚动路径：`EngineDocumentViewer` 只用一次性消费的书签 key 识别自身进度回显，较早发出的同一进度对象再次返回时，会误触发文字书签导航，让参考行从 baseline 对齐变成文字框顶部对齐（约偏移 25px）。现在另用 WeakSet 记录进度对象来源，跨重复回显保留识别能力；外部新书签请求仍正常执行。`test/engine-pdf-progress.test.tsx` 先复现该失败，再验证重复回显及显式书签导航。

加压验证可运行 `PDF_CROP_CYCLES=60 PDF_CROP_FRAMES=4 node scripts/check-pdf-edge-crop.mjs`；默认等待 12 帧，包含阅读进度的 100ms 防抖回显。

最终加压结果：100% 和适宽各 60 轮开关，共 263 项浏览器检查通过，参考 PDF 点最大偏移 0.3125px，无页面错误。导航浏览器回归、106 个文件的 1425 项测试、类型检查、相关 ESLint 与库构建通过。

## 稀疏文字页打开裁边

`two-column.pdf` 暴露了仅锚定阅读区顶部几何点的问题：第 2 页只有靠近页首的一行文字，视口顶端可能位于这行之前的空白处。开启上裁 10% 后，空白锚点被裁掉并夹到裁后页首，但可见文字本身仍在裁切范围内；适宽从约 197% 变为 303% 后，该行从 y=60.5px 跳到 12.640625px。先前密集文字样本把参考点置于视口顶端，未覆盖这段空白。

现在复用书签的首个可见字符查找，取得实际字符矩形并转换为 PDF 坐标，保留其相对安全阅读区顶部的屏幕距离（不使用页内 CSS 偏移作为内容坐标）。这也避免底部留白改变时按视口高度比例挪动文字。没有文字层的页面仍使用几何锚点。

运行 `PDF_CROP_CYCLES=10 node scripts/check-pdf-crop-opening.mjs`：启动本地 Vite，通过 Demo 的上传/加载入口打开原始 `two-column.pdf`，在距滚动底部 0/100/200px 的三个位置各反复开关 10 轮，并检查真实顶部/底部留白输入。脚本直接比较可见文字行的 y，不以理论 viewport 点替代实际文字测量。截图和报告输出至 `test-results/pdf-crop-opening/`。

文档顶部受 scrollTop 非负边界约束：若保持旧文字位置需要负滚动量，按裁后可见页首对齐，保持 scrollTop=0，不添加白色占位。原锚点或文字被裁掉时，也无法承诺它仍显示在原位置；脚本单独检查裁后页首对齐。

钳制后仍需保留切换前的锚点：此前再次关闭裁边时会重新捕获已钳制的位置，导致顶部开关一轮后停在 scrollTop=77。现在检测裁切边界及实际滚动边界是否阻止原锚点恢复，若发生钳制，下一次布局切换继续使用原 PDF 坐标与屏幕位置；用户滚动、跳页、书签、缩放或切换文档仍清除它。浏览器回归增加 scrollTop=0/30/78 各三轮开关，断言关闭后精确回到原滚动值及首行位置；另用真实滚轮移到第 2 页，确认关闭时按新的可见文字恢复。单测分别覆盖文字未裁掉但需负滚动、文字本身被裁掉，以及用户滚动取消旧锚点。

合入主干的新版阅读进度接口后，文字锚点恢复期间返回 pending，避免发布中间位置；无文字页若已有稳定页内比例，则保留主干按裁后显示框重投影的行为，支持立即关闭、重开和旋转恢复。没有稳定比例时仍使用 PDF 几何点。对应的两套回归均保留。跳页测量以阅读容器顶部为基准，避免测试页外层因焦点滚动导致误判；编辑器打开保持阅读位置后，拖拽检查先回到第一页，以确保四个手柄可见。
